# SenseVoice candidate integration status — 2026-10-31

## Implemented

- Opt-in `browser-sensevoice` recognition path with locally packaged SenseVoiceSmall int8, Silero VAD v5 and pinned `@sherpaw/vad-asr@0.3.0` WASM runtime. Existing Zipformer remains the default.
- Exact model, tokens, VAD, runtime archive and extracted runtime file sizes/SHA-256 pinned in `sensevoice-model.lock.json`. Source model and runtime licenses are bundled in the candidate; downloaded binaries stay out of Git.
- 100 ms PCM packets feed 512-sample VAD windows; VAD utterance endings produce final rows, while long speech produces a revisable 5-second interim and a forced 10-second final. The forced final resets VAD at the exact packet boundary and keeps global caption timestamps. Capture/render timing metadata is bounded to 1,200 rows and excludes text and audio.

## Verification completed

- A detached clean checkout passed `npm ci --ignore-scripts`, 61 server tests, 108 extension tests, `npm run typecheck`, `npm run build:sensevoice`, model hash verification and no source maps in the built extension. The clean checkout and its temporary build were removed after verification.
- The actual compiled `sense-worker.js` was loaded in a regular Chrome module worker through a localhost wrapper and fed the first 75 seconds of the official PBS NewsHour Jakarta video as 100 ms PCM packets. It loaded, accepted a reset, emitted revisable interim captions and VAD final captions without worker errors. First three final segments covered the 88-word official PBS reference. This accelerated PCM feed completed in about 34 seconds after worker creation; it does **not** measure real-time tab capture latency.
- Chrome showed roughly 970 MB of memory use for the local probe tab at completion. This is a browser-tab figure, not isolated model RSS or a 60-minute trend.
- A separate 10-second `maxSpeechDuration` browser probe still returned an approximately 15-second first VAD segment; its full-segment decode took about 3.55 seconds. The VAD setting alone does not prove the required ≤3-second P95 final latency. The setting remains 15 seconds in the candidate until real-time accuracy and latency can be compared.
- The compiled worker was also fed the same 75-second PCM at **100 ms wall-clock intervals** in a regular Chrome page. From each aligned packet/utterance audio end to worker event creation, 11 interim events had P50 1,206 ms and P95 2,245 ms; seven final events had P50 3,548 ms and P95 4,809 ms. Peak queued packets were 43, below the extension's 50-packet reset threshold but close to it. These numbers already miss the design's ≤1.5-second interim and ≤3-second final P95 gates **before** offscreen capture, translation and DOM rendering. This local paced probe is a useful rejection signal, not installed-extension acceptance.
- A one-variable local experiment suppressed the second, 10-second full-window interim decode in each VAD utterance. On the same paced input, six remaining interim events had P95 1,173 ms and seven finals had P95 3,727 ms; peak queued packets fell to 34. This confirms repeated provisional decoding causes much of the queue delay, while long full-utterance final decoding still misses the ≤3-second final gate. This experiment was **not** applied to the candidate source because it leaves long gaps between live updates.
- A forced 10-second final is now in the working tree. On the same 75-second wall-clock paced Chrome worker probe, eight interim events had P50 1,131 ms and P95 **1,404 ms**; ten final events had P50 2,095 ms and P95 **2,999 ms**; peak outstanding packets were 25. These are event creation times in a standalone worker, **before** extension capture, translation or DOM rendering. The final gate has essentially no margin, so this does not establish an end-to-end pass.
- The independent [PBS transcript](https://www.pbs.org/newshour/show/jakarta-rapidly-sinks-as-climate-change-and-overdevelopment-collide) was aligned to the first 75 seconds, ending after “a family of seven”; the project's NFKC word metric counted 171 reference words. Native fixed-window SenseVoice WER was **21/171 (12.28%)** at 10 seconds, **18/171 (10.53%)** at 9 seconds, and **29/171 (16.96%)** at 9.5 seconds. In the first 88 words ending at “holding back the tide,” 10 seconds scored **4/88 (4.55%)**, while 9 seconds scored **10/88 (11.36%)**. Nine-second windows damaged some early boundary words and names but made fewer total errors over 75 seconds. The 10-second browser candidate was retained pending a paced 9-second browser comparison and longer reference material. Native and browser scores must not be conflated.
- Stopping the SenseVoice capture now requests a final worker flush before termination, waits at most 8 seconds for the worker and at most 2 more seconds for pending source-history writes. The session also finalizes a voiced tail if VAD flush produces no segment. This closes the previously identified stop-tail loss in source code; real Chrome stop behavior is still unverified.
- The earlier pre-install source passed 61 server and 116 extension tests, typecheck and `build:sensevoice`. Unit tests cover consecutive forced finals, sample continuity, VAD timestamp mapping after a split, silence suppression, a voiced stop tail, Japanese/Korean script labels and Cantonese-to-Chinese same-language handling. The installed source has since changed and requires a fresh final verification.
- Commit `ce11d89` produced a local 346,096,092-byte test ZIP with SHA-256 `0b6746a2db3e5f255f7aa7fa6a296c8b9c62a183985cb97f558fc44e0969836b`. The stale temporary archive was removed to recover disk space.

## Installed Chrome acceptance in progress

- The user approved installing the unlisted local candidate. Chrome loaded it as test extension `ngcobgmdpfijejgjjellpepmoeecpbbn` (447 MB) while the pre-existing CaptionRipple extension was temporarily disabled. A real local `<video>` page at `127.0.0.1:8765` played the PBS news MP4; `tabCapture` showed nonzero RMS, the SenseVoice model reached `running`, and source captions plus Chrome local Chinese translations were visibly rendered and persisted.
- The first installed run exposed `ReferenceError: chrome is not defined` in the ESM worker. Resolving vendor assets from `import.meta.url` fixed model loading in the installed extension. A second run exposed `chrome.storage.local` being unavailable in the offscreen document when recording rendered metrics. The working tree now routes each metric through the background service worker for bounded local storage; the next clean-page run stayed `running` for about 85 seconds without that error.
- That run exported 20 actual capture-to-source-render metrics: nine interims, P50 **1,167 ms**, P95 **1,274 ms**; eleven finals, P50 **2,292 ms**, P95 **2,835 ms**. These are aligned audio-end to first visible **source** caption on the local page. The first 88 PBS reference words had **7/88 WER (7.95%)**; the first 171 words through “a family of seven” had **15/171 WER (8.77%)** from the selected recording's exported final history. The source gates pass on this short local run; finalized Chinese capture-to-render P95 is not instrumented yet.
- Stopping during playback left a final untranslated tail in history. The background stop order was corrected to let the offscreen worker flush and persist the tail before retiring the epoch; this exact fix still needs another installed Chrome run. Earlier `pause` reset the epoch and retained the visible caption, but a partial tail at pause was not finalized into history.
- The Chinese output rendered and many rows translated within tens of milliseconds after final source recognition, but this is translation execution time, not end-to-end translated-render latency. Some sentences were awkward or semantically weak, including the “motorbikes stall” and “for millions like 35-year-old Ratini” lines. The required 50-sentence quality review remains open.
- A subsequent installed 10-second run recorded seven source interims (P95 1,480 ms), nine source finals (P95 2,722 ms) and nine rendered final Chinese captions (P95 2,757 ms). Another 10-second run with first Chinese interim render timing showed interim Chinese P95 **1,570 ms** (three samples) and final Chinese P95 **3,042 ms** (nine samples), exceeding the 1.5/3-second gates. The first interim translation was later shown to incur about 300 ms of startup/translation delay.
- A real installed nine-second forced-split comparison recorded interim source P95 1,357 ms (13), interim Chinese P95 **1,540 ms** (eight), final source P95 2,358 ms (16), and final Chinese P95 2,401 ms (16). The nine-second split cut through clauses and worsened source and Chinese meaning. Using the same 173-word local PBS reference file and the corresponding exported history prefix, the ten-second run scored 10 edits (5.78%) and the nine-second run scored 15 edits (8.67%); these are separate from the earlier 171-word alignment. The forced split was restored to ten seconds. A 75 ms first live-translation scheduling delay and an opt-in local translator warmup remain in source but need installed retesting after that restoration.
- Restored ten-second splits plus translator warmup brought interim Chinese P95 to 1,253 ms (four samples), but final Chinese P95 was 3,216 ms (nine samples), driven by a single 3,188 ms source final. A 9.8-second native fixed-window probe scored 25/173 WER (14.45%) and omitted several short phrases, so it was rejected. A four-thread WASM decoder with ten-second splits then ran about 90 seconds in installed Chrome: interim source P95 1,334 ms (12), interim Chinese P95 **1,286 ms** (five), final source P95 2,554 ms (13), final Chinese P95 **2,584 ms** (13). Using the same 173-word reference and first ten exported final rows, its WER was **7/173 (4.05%)**. These short local samples pass the numerical gates but do not prove broad reliability. A punctuation-only `.` stop-tail was observed and is now suppressed in source; that last change still needs an installed retest.
- The earlier four-thread source passed 61 server and 119 extension tests, typecheck, `build:sensevoice` and `git diff --check`. Its 346,096,804-byte experimental ZIP had SHA-256 `fe8cf7702b8d0d4deae25563bb118d69ff7bc0f1f78ab4cc2789279c1e73bd13`; that stale temporary archive was removed to recover disk space. ## Five-minute FLEURS browser check (new run)

- Each fixture plays official FLEURS speech clips at normal speed in a real local Chrome `<video>` tab; the installed extension uses `tabCapture`, bundled SenseVoice and Chrome local translation. The manifest preserves the independent source text. This is controlled local media, not public live-site acceptance.
- English: the 376-second playback (about 360 seconds of speech) produced 46 final rows and **74/811 WER (9.12%)**, down from **218/811 (26.88%)** before reducing the quiet-speech RMS cutoff from `0.003` to `0.0003`. The current cutoff also kept digital silence suppressed in a focused regression test. Source interim P95 **1,343 ms** (40); Chinese interim P95 **1,431 ms** (31); source final P95 **2,388 ms** (46); Chinese final P95 **2,429 ms** (46).
- Japanese: the 325-second playback (about 302 seconds of speech) produced 43 final rows and **91/1,180 CER (7.71%)**. Source interim P95 **1,404 ms** (27); Chinese interim P95 **1,616 ms** (7); source final P95 **2,737 ms** (43); Chinese final P95 **2,803 ms** (42). One interim translation took 358 ms and missed the 1,500 ms gate. Several translated names and phrases are semantically wrong, and an extra final `我。` appeared after speech ended. Accuracy and latency gates must be judged separately.
- Korean: the 334-second playback (about 305 seconds of speech) produced 42 final rows and **164/1,207 CER (13.59%)**. Source interim P95 **1,360 ms** (35); Chinese interim P95 **1,405 ms** (16); source final P95 **2,543 ms** (42); Chinese final P95 **2,583 ms** (42). Numerical gates pass, while visibly incorrect or awkward Chinese sentences still block the translation-quality gate.
- Cantonese: the 328-second playback (about 303 seconds of speech) produced 44 final rows and **141/881 CER (16.00%)** when compared with an independently prepared Simplified Chinese conversion of FLEURS' Traditional Chinese reference. Source interim P95 **1,346 ms** (34), final P95 **2,692 ms** (44). The same-language Chinese target correctly showed “no translation.” The specification defines a 15% ceiling for **English WER only**; Cantonese CER must still be reported and reviewed for errors. A bounded Chinese numeral normalizer now formats spoken numerals before rendering for explicit Chinese/Cantonese source selection; replaying the saved transcript through that code gives **101/881 CER (11.46%)**, but this has not yet been checked in the installed browser build.
- The current code has passed 61 server and 123 extension tests, typecheck, `build:sensevoice` and `git diff --check`. The installed extension still holds the prior build until a separate Chrome reload is approved and verified.

### Translation spot check

- Reviewed 50 saved source/Chinese pairs from the real Chrome history exports: every third final row from English (16), Japanese (15), and Korean (14), plus English rows 2, 3, 5 and Japanese rows 2, 3. This is a source-to-translation fidelity check, not a blinded reference translation score. The gate does **not** pass: several rows are incomplete because recognition split a clause, and some translations change the meaning even when the source contains the needed word.
- A clear negation failure is Korean row 13: source `불 참석했습니다` (“did not attend”) becomes `出席了` (“attended”). A name error is Japanese `本州列島` rendered `大陆群岛` in another saved row. English `primary grazing` became `主要的放牧地`, and a Japanese one-character `我。` appeared after the audio. These need source-boundary and translation fixes before a stable release.
- A YouTube PBS NewsHour VOD was opened for a real-site probe. The page required a toolbar activation before `tabCapture`; after activation the candidate reconnected and playback began, but the probe was stopped before checking a usable caption history or timing. Record this as attempted, not passed. The original extension was restored as enabled, the candidate test instance disabled, and the local fixture server stopped at the end of this session.

## Still required for release

- Re-test punctuation-only stop-tail filtering in the installed extension, then repeat on external news with independent WER/CER/translation review. Short local English/Chinese runs pass with four decoder threads; broader P95 and quality gates remain unproven.
- Public live media, YouTube, Bilibili, local, iframe and multi-video sites; playback rates; fault recovery; 60-minute stability with resource measurements; at least 5 minutes each of independently referenced English, Japanese, Korean and Cantonese; and 50 reviewed translations.
- The candidate UI now allows explicit Japanese, Korean and Cantonese source selection. Auto speech labels detect Japanese kana and Korean Hangul; Han-only Japanese segments may still be mislabeled Chinese. Cantonese source is routed as Simplified Chinese for translation because this model currently emits Simplified Chinese. Actual Chrome translation availability, model preparation, Japanese/Korean-to-Chinese output and colloquial Cantonese quality remain unverified.
- The standalone probe ends at exactly 75 seconds in the middle of an utterance, so its final transcript omits that tail. Production stop/pause behavior still needs real Chrome verification.
