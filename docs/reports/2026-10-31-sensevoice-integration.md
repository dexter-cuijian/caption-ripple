# SenseVoice candidate integration status — 2026-10-31

## Implemented

- Opt-in `browser-sensevoice` recognition path with locally packaged SenseVoiceSmall int8, Silero VAD v5 and pinned `@sherpaw/vad-asr@0.3.0` WASM runtime. Existing Zipformer remains the default.
- Exact model, tokens, VAD, runtime archive and extracted runtime file sizes/SHA-256 pinned in `sensevoice-model.lock.json`. Source model and runtime licenses are bundled in the candidate; downloaded binaries stay out of Git.
- 100 ms PCM packets feed 512-sample VAD windows; VAD utterance endings produce final rows, while long speech produces a revisable 5-second interim and a forced 10-second final. The forced final resets VAD at the exact packet boundary and keeps global caption timestamps. Capture/render timing metadata is bounded to 1,200 rows and excludes text and audio.

## Verification completed

- A detached clean checkout passed `npm ci --ignore-scripts`, 61 server tests, 108 extension tests, `npm run typecheck`, `npm run build:sensevoice`, model hash verification and no source maps in the built extension. The clean checkout and its temporary build were removed after verification.
- The actual compiled `sense-worker.js` was loaded in a regular Chrome module worker through a localhost wrapper and fed the first 75 seconds of the official PBS NewsHour Jakarta video as 100 ms PCM packets. It loaded, accepted a reset, emitted revisable interim captions and VAD final captions without worker errors. First three final segments covered the 88-word official PBS reference. This accelerated PCM feed completed in about 34 seconds after worker creation; it does **not** measure real-time tab capture latency.
- Chrome showed roughly 970 MB of memory use for the local probe tab at completion. This is a browser-tab figure, not isolated model RSS or a 60-minute trend.
- A separate 10-second `maxSpeechDuration` browser probe still returned an approximately 15-second first VAD segment; its full-segment decode took about 3.55 seconds. The VAD setting alone does not prove the required ≤3-second P95 final latency. The setting remains 15 seconds in the candidate until real-time accuracy and latency can be compared.
- The compiled worker was also fed the same 75-second PCM at **100 ms wall-clock intervals** in a regular Chrome page. From each aligned packet/utterance audio end to worker event creation, 11 interim events had P50 1,206 ms and P95 2,245 ms; seven final events had P50 3,548 ms and P95 4,809 ms. Peak queued packets were 43, below the extension's 50-packet reset threshold but close to it. These numbers already miss the design's ≤1.5-second interim and ≤3-second final P95 gates **before** offscreen capture, translation and DOM rendering. This local paced probe is a useful rejection signal, not installed-extension acceptance.
- A one-variable local experiment suppressed the second, 10-second full-window interim decode in each VAD utterance. On the same paced input, six remaining interim events had P95 1,173 ms and seven finals had P95 3,727 ms; peak queued packets fell to 34. This confirms repeated provisional decoding causes much of the queue delay, while long full-utterance final decoding still misses the ≤3-second final gate. This experiment was **not** applied to the candidate source because it leaves long gaps between live updates.
- A forced 10-second final is now in the working tree. On the same 75-second wall-clock paced Chrome worker probe, eight interim events had P50 1,131 ms and P95 **1,404 ms**; ten final events had P50 2,095 ms and P95 **2,999 ms**; peak outstanding packets were 25. These are event creation times in a standalone worker, **before** extension capture, translation or DOM rendering. The final gate has essentially no margin, so this does not establish an end-to-end pass.
- The independent [PBS transcript](https://www.pbs.org/newshour/show/jakarta-rapidly-sinks-as-climate-change-and-overdevelopment-collide) was aligned to the first 75 seconds, ending after “a family of seven”; the project's NFKC word metric counted 171 reference words. Native fixed-window SenseVoice WER was **21/171 (12.28%)** at 10 seconds, **18/171 (10.53%)** at 9 seconds, and **29/171 (16.96%)** at 9.5 seconds. In the first 88 words ending at “holding back the tide,” 10 seconds scored **4/88 (4.55%)**, while 9 seconds scored **10/88 (11.36%)**. Nine-second windows damaged some early boundary words and names but made fewer total errors over 75 seconds. The 10-second browser candidate was retained pending a paced 9-second browser comparison and longer reference material. Native and browser scores must not be conflated.
- Stopping the SenseVoice capture now requests a final worker flush before termination, waits at most 8 seconds for the worker and at most 2 more seconds for pending source-history writes. The session also finalizes a voiced tail if VAD flush produces no segment. This closes the previously identified stop-tail loss in source code; real Chrome stop behavior is still unverified.
- The current source passes 61 server and 114 extension tests, typecheck and `build:sensevoice`. Unit tests cover consecutive forced finals, sample continuity, VAD timestamp mapping after a split, silence suppression and a voiced stop tail. The new source has **not** yet been installed as an extension.

## Still required for release

- Action-time user confirmation for clean installation of the new 10-second candidate is pending. Then real tabCapture on local and external news, rendered latency P50/P95, and independent WER/CER/translation review are required.
- Public live media, YouTube, Bilibili, local, iframe and multi-video sites; playback rates; fault recovery; 60-minute stability with resource measurements; at least 5 minutes each of independently referenced English, Japanese, Korean and Cantonese; and 50 reviewed translations.
- The standalone probe ends at exactly 75 seconds in the middle of an utterance, so its final transcript omits that tail. Production stop/pause behavior still needs real Chrome verification.

No stable release has been published from this candidate.
